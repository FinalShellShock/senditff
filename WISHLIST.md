## 1. Patch notes / product updates — SHIPPED 2026-07-25

Content lives in `src/data/patchNotes.ts`, newest first. **Every deploy should
add an entry**, covering what changed and what is still broken. A patch note
that only lists wins is marketing, not transparency.

Still open: historical per-release algo fingerprints are not recorded, only the
live build's, so feedback still traces to a hash rather than to a release name.

Original ask below.

A link in the footer that opens a popup, most recent release at the top.

Every deployment should ship with a written patch note covering:

- what changed in this release
- known bugs currently being worked on

**Why it matters:** there are real users now (not just Johnny), and the
algorithm changes underneath them constantly. A trade that made sense last week
may not appear this week, and right now nothing explains why. Patch notes turn
"the app is inconsistent" into "the app is improving."

**Implementation notes:** the algo fingerprint (`src/algo/version.ts`,
generated by `scripts/build-api.mjs`) already changes on every meaningful
algorithm edit, so a release entry could carry its fingerprint and let feedback
be traced to a human-readable release rather than a hash.

## 2. General site feedback (HIGH PRIORITY)

Feedback about the **site**, not just about a specific trade. A small button in
the footer, next to Recent updates / Privacy / Terms.

**Johnny (2026-07-25):** high priority, deferred only because he was about to
hit a session limit.

**Why it matters:** the trade thumbs only capture "was this trade good." They
cannot capture "the overview page confused me", "this label is wrong", "I
expected X and got Y". Every UI problem found so far came from Johnny noticing
it himself, which does not scale past one user, and the other three have no way
to report anything.

**Implementation notes:** `POST /api/feedback` already exists and already
server-stamps identity, time, `algoVersion`, and `algoFingerprint`. Site
feedback is the same write with a different shape: no trade package, plus the
current route so a report lands somewhere specific. Worth adding a `kind`
field (`"trade"` or `"site"`) so `scripts/feedback-export.ts` can split them,
since mixing free-form site complaints into the algorithm tuning data would
poison the signal that export exists to produce.

Pairs naturally with entry 3, the unread notification: both are about closing
the loop between users noticing something and Johnny hearing about it.

## 3. New-feedback notification

Some way for Johnny to see that someone has submitted feedback without going
looking for it. A small bell or badge in the footer:

> "3 new feedback submissions"

It clears every time the feedback is pulled and acted on.

**Johnny's note (2026-07-25):** "probably sooner than later."

**Why it matters:** feedback is the only tuning signal this app has, and right
now it sits silently in Firestore until someone remembers to run the export.
The whole loop depends on Johnny knowing there is something to look at.

**Implementation notes:** the clearing mechanism already exists.
`scripts/feedback-export.ts` stamps `pulledAt` on every entry it pulls, so the
unread count is just a count of feedback documents missing that field. No new
data model, no new write path, and the count cannot drift out of sync with what
was actually acted on because the export is what sets it.

The read side needs a tiny authed endpoint (count only, no payload) since the
client cannot query the feedback collection directly. Worth restricting to
Johnny's uid, since it is an admin signal and not something the other users
should see.

## 4. Trade scenario simulation builder

"The move after the move." Chain hypothetical trades and see where the roster
lands.

- Stack several trades in sequence: *if I make this trade, then this one, and
  everyone accepts, what does my team look like?*
- Report where the roster got **stronger** and where it got **weaker**
- Possibly a **league shape summary**: how the league as a whole changed, not
  just the one roster

**Why it matters:** single-trade evaluation can't express a strategy. Real
dynasty managers think two or three moves ahead, and the app currently forces
them to evaluate each step blind to the others.

**Implementation notes:** `simulateImpact()` in `api/_lib/tradeEngine.ts`
already computes post-trade position scores for both sides. The core math for
one hop exists; the work is sequencing hops, keeping a mutable roster state
across them, and diffing the start and end profiles. The Shotgun projection
(`src/algo/projection.ts`) is the natural fit for the "and then how does it
age" part of the answer.

## 5. Trade Tinder

Managers opt in to trade archetypes they'd be interested in. When two managers
in the same league mark **complementary** archetypes, both get a nudge.

**Critical constraint, from Johnny:** never reveal the actual trades either
side was considering. That would give up leverage. The signal is only:

> "Team X is also interested in a trade like this."

**Why it matters:** the hardest part of dynasty trading is not finding a good
trade, it's finding a willing counterparty. This solves discovery without
leaking anyone's hand.

**Implementation notes:** `COUNTER_ARCHETYPES` in `api/_lib/tradeEngine.ts`
already encodes which archetypes pair with which (tier_down pairs with
consolidate, age_arb_buy with age_arb_sell, and so on). That map is the
matchmaking logic, already written and already tested in scoring.

## 6. Saved trades / drafts

Draft a trade, save it, come back to it.

- A drafts page or sub-tab listing saved trades
- Tinker with a saved trade and re-evaluate it
- **Track how each side's value has moved over the last 7 / 15 / 30 days**
- Attach personal notes to a draft

**Ties into Trade Tinder:** a user's drafts are a stronger, more honest signal
of intent than a checkbox, because they reflect what someone actually built
rather than what they said they wanted. That enables the match nudge:

> "It's a match! This team is looking to consolidate while you're looking to
> tier down. Send it?"

**Why it matters:** trade values drift. A package that was fair when drafted
may be a steal or a joke two weeks later, and nothing surfaces that today.

**Implementation notes (drafts):** value-over-time needs historical value snapshots.
`valueSnapshots/{formatKey}` in Firestore currently stores only the latest pull
and overwrites it, so **dated snapshots would need to be retained first** —
that's the prerequisite, and it's cheap to start now even if the feature is
later. Every day not retained is history that can't be recovered.

## 7. Additional fantasy platforms — MyFantasyLeague (MFL) first

Support leagues hosted somewhere other than Sleeper. MFL is the first target.

**Yes, MFL has a usable API.** Verified live 2026-07-25: free, no auth, no key,
returns JSON.

```
https://api.myfantasyleague.com/{year}/export?TYPE=players&JSON=1&DETAILS=1
https://api.myfantasyleague.com/{year}/api_info        # request reference
```

The players export returns 2,590 records (919 at QB/RB/WR/TE), ~890KB with
`DETAILS=1`. `TYPE=league`, `TYPE=rosters`, and the rest of the export types
follow the same shape and take a league id via `&L=`.

### What lands in our favor

- **`birthdate` is included** (unix timestamp), so exact decimal ages come
  straight from the source, the same way we derive them from Sleeper. Age is
  load-bearing in this app, so this matters more than it sounds.
- **`espn_id` is present on 2,121 records**, and nflverse `players.csv` also
  carries `espn_id`. That gives an ID-based join to the aging research instead
  of a name join, which is strictly better than what we do for Sleeper today.
- Also carries `rotowire_id`, `stats_id`, `cbs_id`, `sportsdata_id`,
  `draft_year`, `draft_round`, `college`.

### Three traps to plan around

1. **Names are "Last, First"** — the API returns `"Brady, Tom"`. Our `normName`
   strips non-alphanumerics, so that becomes `bradytom` while Sleeper's
   `"Tom Brady"` becomes `tombrady`. **They will not match, and the failure is
   silent** (zero joins, no error). MFL names have to be reversed before
   normalization. This exact class of bug already bit us once on the QB signals
   join, so treat it as a known landmine rather than a detail.
2. **No `sleeper_id` and no `gsis_id`.** Cross-platform identity has to route
   through `espn_id` or normalized names.
3. **IDP is everywhere.** Roughly 1,150 of the 2,590 records are IDP positions
   (LB, CB, DT, DE, S). MFL leagues run IDP far more often than Sleeper ones,
   and we currently reject IDP leagues outright with a 422. Expect a meaningful
   share of MFL leagues to bounce until IDP is actually supported. Worth
   deciding up front whether MFL support implies IDP support.

### Architectural note

`src/data/sleeper.ts` is currently the only league source, and `detectFormat`,
`buildTeams`, and the sync endpoint all assume its shapes. Adding a second
platform is the moment to define a **provider interface** (fetch league, fetch
rosters, fetch traded picks, detect format) with Sleeper and MFL as two
implementations, rather than branching inside the existing functions. Doing it
at two providers is cheap; doing it at four is a rewrite.
